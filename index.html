lfs-rl · project overview

Verifiable debugging tasks for training and evaluating agents, derived from failures Claude Fable 5 made in real operation.

We operated Claude Fable 5 as the administrator of a real Linux system over several months and recorded its failures. The model rarely failed to repair a problem it had been given. It failed to notice that something was wrong at all, often hours after the original mistake and with the evidence pointing elsewhere. The tasks are constructed directly from those recorded failures.

Every task is graded by the same procedure. A program is compiled and run inside the repaired system, and it either produces the correct output or it does not. No judge model is involved, and there is no answer string to match. The grading also resists gaming. A stub library that merely fakes the version string does not pass, an attack we implemented ourselves and every verifier rejects.

Example episode. A cross-package fault (symptom in one package, cause in another)
$ chroot /mnt/lfs make -C /sources/kmod-34.2
/usr/bin/ld: undefined reference to `gzread' # symptom, kmod won't link
$ ls -l /usr/lib/libz.so
libz.so -> libbz2.so.1.0 # cause, zlib's dev symlink is mispointed
$ ln -sf libz.so.1.3.1 /usr/lib/libz.so && make && make install
verifier: libkmod compiles, links, and runs (reward 1.0)

Three task classes

The project's tasks fall into three classes at different stages of maturity. The distinction matters because only the first class has measured results.

Short-horizon repair, evaluated. The agent is told which package is broken and must diagnose and repair it, one shell command per turn. The set holds 74 instances across five library packages, including a group in which the evidence is misleading and the error output implicates the wrong component. Each instance is machine-verified before it enters, the reference fix must pass the verifier and a naive rebuild must not. A Qwen2.5-3B model trains end-to-end on this tier, and the table below reports full-solve on the trained faults at each stage, no training, then supervised warm-start, then GRPO. The central finding is that adding more training faults alone produced no transfer, the model reproduced what it was shown without learning to diagnose. Transfer appeared only after the demonstrations were redesigned so that every trajectory shows the discriminating check and continues based on its visible output. With that design, full-solve on held-out instances went from 0% base to 33% after supervised fine-tuning to 58% after a five-round GRPO probe. A frontier model solves a representative subset of these scoped tasks zero-shot in 7 to 18 commands, each pass confirmed by the verifier rather than self-reported, so this tier's present value is the training and evaluation of open models.

Training performance, short-horizon tier. Binary full-solve on the 18 trained faults, Qwen2.5-3B (the repaired system must run correctly, not merely build). One rollout per fault. The gain from base to GRPO is significant (paired p = 0.004) and corroborated by training-time pass rates, while the step from warm-start to GRPO alone is directional, not precise.

Long-horizon localization, built but not yet evaluated. A fault is planted in one package, the build continues normally, and the breakage surfaces up to fourteen packages later. The agent is told nothing about where to look. Four instances pass every machine check, spanning two fault mechanisms, a corrupted artifact consumed downstream and a configuration lie the downstream package silently acts on. No model has been trained or systematically evaluated on this tier. A single frontier calibration episode is the only measurement to date.

Ops-derived procedural tasks, built but not yet evaluated. Two task families derived from a single real incident, recorded while a frontier model operated a live Linux system. Neither involves injected sabotage. In the first, the agent holds an upgrade script written for a chroot and must apply a security update to the running system. Reusing the script's in-place install on the new version replaces a library the running shell still depends on and leaves the machine unusable. In the second, an upgrade wrapper completes its work correctly and then reports failure, because its own verification step loses a scheduling race. The agent must show the system is healthy, repair the check so the race is gone, and inspect sibling scripts for the same defect. Each family passes its own machine gate (four checked end states for the first, six for the second, and every case triggers exactly the check intended for it). Like the long-horizon tier, they have no model results yet.

The long-horizon tier in numbers

Tasks verified
4, each passing 3 machine-checked properties (the fault causes a verified failure, repairing only the package where the symptom appears does not pass, repairing the true cause does)
Candidates rejected
2 of the 6 candidate tasks built to date failed one of the three properties and were removed, and the other 4 are the verified set above, so no candidate is pending. The rejections are reported because they show the checker filters rather than approves everything. Both rejected candidates are closed. One is retired because measurement showed no seed of its kind can work on this substrate. The other's mechanism was rebuilt as a new candidate against a package that actually reads the lied-about value, and that new candidate is among the 4 verified.
Cause-to-symptom distance
the number of packages built between the faulty package and the package where the build visibly fails. The four verified tasks measure 5, 5, 14, and 3.
Difficulty control
one fault family is verified at both distance 5 and distance 14, so difficulty is set by a generator parameter rather than by new design work
Expansion capacity
82 packages are built downstream of the fault-injection point, each a possible site for the symptom to surface
Frontier baseline
Claude Fable 5 solved the easiest instance in 24 of the 40 permitted commands, through genuine diagnosis rather than a memorized repair
Model results
none yet, no training run and no multi-sample evaluation has been performed on this tier

Environment properties

Format
packaged as a verifiers environment and validated end-to-end against a live model endpoint
Determinism
the same seed reproduces the same fault and the same verifier
Cost
rootless sandbox, about 1.6 seconds and 200 MB per episode, and a full training run cost about $0.50 of GPU time
Isolation
the sandbox runs untrusted agent-generated shell behind an allow-list filesystem and a private loopback-only network, verified by writing markers into every host path from inside and confirming none reached the host
Scaling
faults are parameterized over the package, so adding a library reuses the whole taxonomy for one small verifier and one entry

Design basis

The environment follows three published designs. RLVE matches task difficulty to the model being trained. That principle is applied now and is the reason distance is a parameter. BPO forks rollouts from sandbox snapshots. It is the reason the substrate can fork an episode at any package instead of rebuilding from scratch. TRACE assigns credit to individual steps of a long task. Its adaptation to our state-based grading is worked out and waits for training to begin.

lfs-rl is intended for teams and platforms that train or evaluate open models on agentic, coding, or operations tasks, and for RL-environment marketplaces that require verifiable, hard-to-game rewards.

The environment and its full results remain in a private repository. This page is the standing summary of what exists, what has been measured, and what has not.
