Technical summary

lfs-rl, a verifiable RL environment for systems-debugging agents

An agent diagnoses and repairs a fault injected into a fully-built Linux system. The reward is a functional check run inside the repaired system, not a string match.

RLVR·reward-hack-resistant·verifiers-compatible·74 fault instances·deterministic
Abstract

lfs-rl is a reinforcement-learning environment in which an agent diagnoses and repairs a fault injected into a fully-built Linux From Scratch system, using a shell and no hints. An out-of-band verifier runs a program inside the repaired system, so the reward resists gaming. With the included pipeline (supervised warm-start, then GRPO) a Qwen2.5-3B trains end-to-end on an 18-fault curriculum, reaching 50% binary full-solve on trained faults from a 0% base rate. On faults that require a repair step before the rebuild — removing a sabotaged compiler configuration — the base model scores 0% and the supervised warm-start reaches it only intermittently (33%), while GRPO converges on it reliably, reaching 100% across every package that has it; that particular repair happens to be phrased identically regardless of package, which is a large part of why it generalizes — a caveat this project takes seriously enough that it is now redesigning the training data to demonstrate genuine diagnosis (see below) rather than assume exploration alone accounts for it. Generalization to held-out fault types and packages stays flat at 8% regardless of curriculum size, cleanly separating procedural mastery from genuine diagnosis. On a representative subset, a frontier model solves the scoped tasks zero-shot — notably, several fault mechanisms are distilled from failures that fooled frontier models in real operation, so the benchmark is the clean, verifiable version of problems that are hard in the wild.

1Environment

Each episode begins from a working Linux From Scratch (LFS) chroot with a single injected fault. The set contains 74 deterministic instances across five library packages and a broad fault taxonomy, from toolchain sabotage and cross-package breaks to runtime-correctness faults where the library builds but returns wrong data. A distinct tranche models realistic operational failure modes in which the evidence lies, a header quietly shadowed by a stale one, a make that is secretly a dry run and writes nothing while exiting 0, a downloaded tarball that is really a saved error page, a library that keeps winning at load time after a clean rebuild. In these the error blames the wrong thing, so the agent must genuinely diagnose rather than pattern-match a known repair. The agent gets a shell with sudo and no network, one command per turn. Episodes run in a rootless sandbox at about 1.6 seconds each, which makes on-policy RL over real package builds practical.

Example episode. A cross-package fault (symptom in one package, cause in another)
$ chroot /mnt/lfs make -C /sources/kmod-34.2
/usr/bin/ld: undefined reference to `gzread' # symptom: kmod won't link
$ ls -l /usr/lib/libz.so
libz.so -> libbz2.so.1.0 # cause: zlib's dev symlink is mispointed
$ ln -sf libz.so.1.3.1 /usr/lib/libz.so && make && make install
verifier: libkmod compiles, links, and runs (reward 1.0)

2Verifiable reward

A functional verifier scores each episode out-of-band. It compiles a small canary program inside the repaired system, runs it, and compares the output against ground truth, for example a compress/decompress round-trip. The reward reflects whether the repair actually works, not whether the expected files are present. A stub library that only fakes the version string does not pass. We implemented that attack ourselves and every verifier rejects it. A dense shaped reward over milestones gives a weak base policy gradient, and a binary reward is used for evaluation. Adding a package needs only a new canary, and an automated check proves each new fault both solvable (the reference fix passes) and biting (a naive rebuild does not) before it enters the set.

3Training result

We regenerate a supervised warm-start (90 oracle reference-fix trajectories spanning all 18 training faults), then run GRPO with a shaped reward on a single GPU, serving generation through vLLM with the adapter hot-loaded each round. Training converged after six gradient updates: mean shaped reward climbed from 0.21 to 0.60, and the seventh round hit zero within-group variance, every fault had settled into a uniform pass or uniform fail across its group, leaving nothing left for GRPO to learn from. RL learns a repair supervision could not fully teach — but only within one fault category, and we traced why. The warm-start reliably reproduces a package rebuild (3 / 4 clean-rebuild instances, matched by GRPO) and picks up the compiler-spec repair on one of three packages, but the GRPO gain concentrates entirely in toolchain-type faults (6 / 9, 67%) versus zero on the faults modeling realistic operational failure, where the evidence itself misleads (0 / 3). Auditing the warm-start data explains the split: it is generated by replaying each fault's reference fix directly, with no diagnostic step shown, ever. For the toolchain faults that fix happens to be one command that is identical across every package (a coincidence of how gcc's own tooling reports the path); the model only has to reproduce one memorized string, and that trivially looks like it transfers. For the faults that require locating something package-specific — a stray header, a swapped-out build tool — there is no shared string to fall back on, and the data never demonstrated how to find one either. We then rewrote the warm-start generator for these faults to include the investigative command (list the suspect directory, run file on the suspect artifact) ahead of the fix, retrained, and saw no movement (held-out 0 / 13, targeted faults still 0 in-distribution) — and a subsequent setup audit showed why that run cannot settle the question: the demonstrated diagnostic step was constant per fault family, with a fix that never depended on what the evidence revealed, so the data could not teach observation-conditioned diagnosis even in principle, and its single-sample eval deltas carry no statistical weight. The audit also surfaced sampler and regularization flaws (now fixed) affecting all runs equally. What stands across four mutually consistent runs is the environment's core claim: it cleanly and reproducibly measures the memorization-versus-diagnosis gap in small open models — GRPO beats the base model in-distribution decisively (paired p = 0.004) while transfer to genuinely unseen faults stays at zero. The properly designed demonstrations experiment (evidence-conditioned instances, multi-sample evals, an RL probe) is specified and pending.

Generalization is measured, not assumed, and does not move with curriculum size. Tripling the training curriculum from 6 to 18 faults nearly doubled the final GRPO in-distribution rate versus a smaller earlier run on the same environment (28% → 50%), but held-out transfer stayed exactly flat at 1 / 13 (8%) both before and after GRPO on this run. That one pass is a trained fault resampled under the eval harness, not a genuinely unseen instance; every truly held-out cell (unseen fault type, unseen package, unseen composite, unseen combination of both) is 0% for every policy tested, including GRPO. Every fault in the environment, trained or held-out, is proven solvable by its reference fix and unsolved by a naive rebuild before it enters the set. The finding this scaling run was built to test: training-fault diversity is not the lever that closes the memorization-versus-diagnosis gap — the trained model reliably reproduces more of what it was shown, not how to diagnose something new. An earlier, larger run (13 fault types, ~111 warm-start trajectories, on a since-rebuilt environment, later found to have eval/train overlap in the warm-start data) reached 90% in-distribution; the number above is the more rigorously split, currently reproducible one.

4Difficulty calibration

We measured a frontier model on a representative subset of faults via a sub-agent harness, one attempt each, each result independently confirmed by the harness's own verifier (not the agent's self-report) before the instance was torn down. On the earlier tiers it solved them in 8 to 11 commands; the evidence-lies tranche pushes deeper — 6/6 verified pass, in 7 to 18 commands, since whole families of hypotheses must be eliminated when the error blames the wrong thing (the composite fault, two independent root causes in one instance, took the most). An important nuance: several of those mechanisms are distilled from failures that actually fooled frontier models operating a real system — the benchmark scopes the task ("this package is broken, repair it"), which is easier than the operational original, where the model had to notice the problem itself amid misleading evidence. So the scoped tasks are within frontier reach, which makes the environment's value today its training and evaluation of open models, where it resolves the capability gradient from 0% up.

5Integration and cost

  • FormatPackaged as a verifiers environment and validated end-to-end against a live model endpoint.
  • DeterminismThe same seed reproduces the same fault and verifier.
  • FootprintRootless sandbox, ~1.6 s/episode, ~200 MB per instance. A full training run cost about $0.50 of GPU.
  • IsolationThe sandbox runs untrusted, agent-generated shell. Its filesystem view is allow-list, only the directories a build needs are kept and everything else on the host is shadowed, with a private loopback-only network. Verified by writing a marker into every host path from inside and confirming none reached the host.
  • IncludedThe environment, fault generator, end-to-end training pipeline and recipe (which reproduces the results above), and the calibration harness.
  • ScalingFaults are parameterised over the package, so each new library reuses the whole taxonomy for a small verifier and one entry; the set has grown to 74 faults, each proven solvable and biting by CI. Further packages are staged.

6Fit and availability

lfs-rl is intended for teams and platforms that train or evaluate open models on agentic, coding, or operations tasks, and for RL-environment marketplaces that require verifiable, hard-to-game rewards.

The full environment, training pipeline, and calibration data are available for evaluation. We welcome a technical review.
