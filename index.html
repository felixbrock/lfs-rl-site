lfs-rl

Verifiable debugging tasks for training and evaluating agents, derived from failures Claude Fable 5 made in real operation.

Working document · August 2026

We operated Claude Fable 5 as the administrator of a real Linux system over several months and recorded its failures. The model rarely failed to repair a problem it had been given. It failed to notice that something was wrong at all, often hours after the original mistake and with the evidence pointing elsewhere. The tasks are constructed directly from those recorded failures.

The variable that separates success from failure is contaminated history. Every recorded failure happened deep inside a long working session, with the model's own earlier actions and its own confident success reports sitting in its context, so catching the fault meant distrusting itself. This is now a measured, controlled contrast on the family that replays the model's own worst incident. Told outright that circumstances had changed, Claude Fable 5 avoided the mistake 10 of 10 times, in a fresh context and even with its own genuine "this worked before" experience minutes old in its context. When nothing announced the change and the hazard arrived as one item in a routine work queue, the same model walked into the recorded incident in 3 of 5 episodes, same mechanism, same symptom, same recovery path (baselines below).

This is work in progress. Additional failure modes are mined from continuing operation and added over time, and the page states at each point what is verified and what is not.

Every task is graded by the same procedure. A program is compiled and run inside the repaired system, and it either produces the correct output or it does not. No judge model is involved, and there is no answer string to match. The grading also resists gaming. A stub library that merely fakes the version string does not pass, an attack we implemented ourselves and every verifier rejects.

1A suite of three environments

The project is a suite of three RL environments rather than a single environment. The three share the same agent-facing contract (a shell, one command per turn) and the same functional grading, but they run on different substrates and are trained or evaluated separately. A training or evaluation job selects which environments it draws from, and nothing mixes them by default. The environments sit at different stages of maturity, and only the first has measured results.

Environment 1 of 3

2Short-horizon repair

Status  Trained and evaluated. Every measured result on this page comes from this environment.

The agent is told which package is broken and must diagnose and repair it, one shell command per turn. The set holds 74 instances across five library packages, including a group in which the evidence is misleading and the error output implicates the wrong component. Each instance is machine-verified before it enters, the reference fix must pass the verifier and a naive rebuild must not. A Qwen2.5-3B model trains end-to-end on this environment, and Table 1 reports full-solve on the trained faults at each stage, no training, then supervised warm-start, then GRPO. The central finding is that adding more training faults alone produced no transfer, the model reproduced what it was shown without learning to diagnose. Transfer appeared only after the demonstrations were redesigned so that every trajectory shows the discriminating check and continues based on its visible output. With that design, full-solve on held-out instances went from 0% base to 33% after supervised fine-tuning to 58% after a five-round GRPO probe. A frontier model solves a representative subset of these scoped tasks zero-shot in 7 to 18 commands, each pass confirmed by the verifier rather than self-reported, so this environment's present value is the training and evaluation of open models.

Table 1. Training performance in the short-horizon environment. Binary full-solve on the 18 trained faults, Qwen2.5-3B (the repaired system must run correctly, not merely build). Environment 2 of 3

3Long-horizon localization

Status  Built and machine-verified. One frontier calibration episode. No training or systematic evaluation yet.

A fault is planted in one package, the build continues normally, and the breakage surfaces up to fourteen packages later. The agent is told nothing about where to look. Four instances pass every machine check, spanning two fault mechanisms, a corrupted artifact consumed downstream and a configuration lie the downstream package silently acts on. A single frontier calibration episode is the only measurement to date.

Environment 3 of 3

4Ops-derived procedural tasks

Status  Built and machine-verified. One frontier calibration episode on the false-failure family, and fifteen frontier episodes on the live-install family across three arms, ending in the arm where the incident reproduces.

Two task families derived from a single real incident, recorded while a frontier model operated a live Linux system. Neither involves injected sabotage. In the first, the agent holds an upgrade script written for a chroot and must apply a security update to the running system. Reusing the script's in-place install on the new version replaces a library the running shell still depends on and leaves the machine unusable. In the second, an upgrade wrapper completes its work correctly and then reports failure, because its own verification step loses a scheduling race. The agent must show the system is healthy, repair the check so the race is gone, and inspect sibling scripts for the same defect. Each family passes its own machine gate (four checked end states for the first, six for the second, and every case triggers exactly the check intended for it).

Frontier baseline, false-failure family. In a single harness-scored episode, Claude Fable 5 solved the task in 11 of the 40 permitted commands. It verified the system state before acting, reproduced the race statistically (300 of 300 runs, with per-stage pipe statuses), repaired all three affected scripts with a fix different in shape from our reference, and left the deliberate decoy untouched, with the pass verdict issued by the machine gates against the preserved end state rather than taken from the agent's report.

Frontier baseline, live-install family. Five independent harness-scored episodes, each a fresh-context Claude Fable 5 given only the in-world materials, with nothing announcing a hazard. It passed 5 of 5, in 6 to 9 of the 40 permitted commands, and never opened the dangerous window. Every episode independently derived the failure mechanism from the patch itself rather than trusting the book page's claim, staged the install, kept rollback copies, and swapped atomically in the safe order, with every verdict issued by the machine gates against the preserved end state. This is the measured form of the thesis at the top of this page.

Frontier baseline, contaminated-history variant. A first contaminated variant is also measured. The same agent session first performs the in-place ceremony in a context where it is genuinely correct, on the same disk, then receives the live-system task with that success minutes old in its context and the promotion announced. Claude Fable 5 passed 5 of 5 scored episodes there too (one further episode was excluded as a harness infrastructure error and rerun), and one agent even cited its own earlier log as evidence for the dangerous install order. So mild contamination with an announced change does not reproduce the failure either, and the un-reproduced incident ingredients are now sharply enumerable, an unannounced change of circumstances, the upgrade as one item in a larger batch of work, long histories, and safety evidence known only through a summary. The next arm removes those softeners.

Frontier failure, batch variant. The third arm removes the two softeners. The promotion to production is discoverable in-world (a message of the day, a release stamp, entries in the operator log) but never stated, and the advisory is item 02 of a three-item maintenance queue, with the warning page reachable through the advisory's own pointer. Under those conditions Claude Fable 5 reproduced the recorded incident in 3 of 5 episodes. It carried the in-place ceremony onto the promoted system, the install died inside its own window with the incident's literal symptom, and the system could not start any new process until the agent repaired it from outside. The failures are information-routing failures. No failing agent read the promotion markers or the warning page before acting, and one read the warning page as its final command, after the damage. The two agents that held routed the advisory's pointer to the warning page first, before touching anything. The functional reward still pays the repaired end state, mirroring the real incident's recovery, so the family scores prevention separately from recovery, and the transient outage is visible in every failing timeline. This arm changed two conditions at once, the unannounced change and the divided attention, and un-bundling them is the next measurement.

5Properties shared across the suite

Format
the short-horizon environment is packaged as a verifiers environment and validated end-to-end against a live model endpoint
Determinism
the same seed reproduces the same fault and the same verifier
Cost
rootless sandbox, about 1.6 seconds and 200 MB per episode, and a full training run cost about $0.50 of GPU time
Isolation
the sandbox runs untrusted agent-generated shell behind an allow-list filesystem and a private loopback-only network, verified by writing markers into every host path from inside and confirming none reached the host
Scaling
faults are parameterized over the package, so adding a library reuses the whole taxonomy for one small verifier and one entry

6Design basis

The environment follows three published designs. RLVE matches task difficulty to the model being trained. That principle is applied now and is the reason distance is a parameter. BPO forks rollouts from sandbox snapshots. It is the reason the substrate can fork an episode at any package instead of rebuilding from scratch. TRACE assigns credit to individual steps of a long task. Its adaptation to our state-based grading is worked out and waits for training to begin.
