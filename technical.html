Technical summary

lfs-rl, a verifiable RL environment for systems-debugging agents

An agent diagnoses and repairs a fault injected into a fully-built Linux system. The reward is a functional check run inside the repaired system, not a string match.

RLVR·reward-hack-resistant·verifiers-compatible·74 short-horizon faults·long-horizon tier staged·deterministic
Abstract

lfs-rl is a reinforcement-learning environment in which an agent diagnoses and repairs a fault injected into a fully-built Linux From Scratch system, using a shell and no hints. An out-of-band verifier runs a program inside the repaired system, so the reward resists gaming. The project has two task tiers at different stages of maturity, and every quantitative result on this page comes from the short-horizon tier, where each task is scoped to a named broken package. On that tier a Qwen2.5-3B trains end-to-end with the included pipeline (supervised warm-start, then GRPO), reaching 50% binary full-solve on an 18-fault curriculum from a 0% base rate, and a demonstration-design experiment produced genuine observation-conditioned transfer, 0% base to 33% supervised to 58% after a five-round GRPO probe on held-out instances. A frontier model solves a representative subset of the scoped tasks zero-shot. Notably, several fault mechanisms are distilled from failures that fooled frontier models in real operation, so the benchmark is the clean, verifiable version of problems that are hard in the wild. The long-horizon tier plants a fault early in a real build sequence and lets the symptom surface up to fourteen packages later, with the agent told nothing about where to look. That tier is built and machine-verified, and it has no evaluation results yet beyond a single frontier calibration episode.

1Two task tiers, and which one the results come from

The environment contains two kinds of task, and they should not be read as one benchmark. The short-horizon tier scopes each episode to a single named broken package, and it is the tier that has been trained on and evaluated. The long-horizon tier removes the scoping entirely, the fault sits packages away from the symptom and the agent must localize it first. That tier exists and passes its machine checks, but no model has been trained on it and no systematic evaluation has been run. Sections 2 through 5 describe the short-horizon tier and its measured results. Section 6 describes the long-horizon tier and states exactly what is and is not known about it.

2The short-horizon environment

Each episode begins from a working Linux From Scratch (LFS) chroot with a single injected fault. The set contains 74 deterministic instances across five library packages and a broad fault taxonomy, from toolchain sabotage and cross-package breaks to runtime-correctness faults where the library builds but returns wrong data. A distinct tranche models realistic operational failure modes in which the evidence lies, a header quietly shadowed by a stale one, a make that is secretly a dry run and writes nothing while exiting 0, a downloaded tarball that is really a saved error page, a library that keeps winning at load time after a clean rebuild. In these the error blames the wrong thing, so the agent must genuinely diagnose rather than pattern-match a known repair. The agent gets a shell with sudo and no network, one command per turn. Episodes run in a rootless sandbox at about 1.6 seconds each, which makes on-policy RL over real package builds practical.

Example episode. A cross-package fault (symptom in one package, cause in another)
$ chroot /mnt/lfs make -C /sources/kmod-34.2
/usr/bin/ld: undefined reference to `gzread' # symptom, kmod won't link
$ ls -l /usr/lib/libz.so
libz.so -> libbz2.so.1.0 # cause, zlib's dev symlink is mispointed
$ ln -sf libz.so.1.3.1 /usr/lib/libz.so && make && make install
verifier: libkmod compiles, links, and runs (reward 1.0)

3Verifiable reward

A functional verifier scores each episode out-of-band. It compiles a small canary program inside the repaired system, runs it, and compares the output against ground truth, for example a compress/decompress round-trip. The reward reflects whether the repair actually works, not whether the expected files are present. A stub library that only fakes the version string does not pass. We implemented that attack ourselves and every verifier rejects it. A dense shaped reward over milestones gives a weak base policy gradient, and a binary reward is used for evaluation. Adding a package needs only a new canary, and an automated check proves each new fault both solvable (the reference fix passes) and biting (a naive rebuild does not) before it enters the set.

4Training results, short-horizon

We regenerate a supervised warm-start (90 oracle reference-fix trajectories spanning all 18 training faults), then run GRPO with a shaped reward on a single GPU, serving generation through vLLM with the adapter hot-loaded each round. Training converged after six gradient updates. Mean shaped reward climbed from 0.21 to 0.60, and the seventh round hit zero within-group variance, every fault had settled into a uniform pass or uniform fail across its group, leaving nothing left for GRPO to learn from. RL learns a repair supervision could not fully teach, but only within one fault category, and we traced why. The warm-start reliably reproduces a package rebuild (3 / 4 clean-rebuild instances, matched by GRPO) and picks up the compiler-spec repair on one of three packages, but the GRPO gain concentrates entirely in toolchain-type faults (6 / 9, 67%) versus zero on the faults modeling realistic operational failure, where the evidence itself misleads (0 / 3). Auditing the warm-start data explains the split. It is generated by replaying each fault's reference fix directly, with no diagnostic step shown, ever. For the toolchain faults that fix happens to be one command that is identical across every package (a coincidence of how gcc's own tooling reports the path), so the model only has to reproduce one memorized string, and that trivially looks like it transfers. For the faults that require locating something package-specific, a stray header or a swapped-out build tool, there is no shared string to fall back on, and the data never demonstrated how to find one either. We then rewrote the warm-start generator for these faults to include the investigative command (list the suspect directory, run file on the suspect artifact) ahead of the fix, retrained, and saw no movement (held-out 0 / 13, targeted faults still 0 in-distribution). A subsequent setup audit showed why that run cannot settle the question. The demonstrated diagnostic step was constant per fault family, with a fix that never depended on what the evidence revealed, so the data could not teach observation-conditioned diagnosis even in principle, and its single-sample eval deltas carry no statistical weight. The audit also surfaced sampler and regularization flaws (now fixed) affecting all runs equally.

What stands across four mutually consistent runs is the environment's core claim, that it cleanly and reproducibly measures the memorization-versus-diagnosis gap in small open models. GRPO beats the base model in-distribution decisively (paired p = 0.004) while transfer to genuinely unseen faults stays at zero under ritual-style training data. The properly designed experiment was then run. A new fault family hides the repair target at an instance-specific path named only inside a script the agent must read, demonstrations show the discriminating check in every trajectory with the continuation branching on its visible outcome, and evals keep full transcripts at four samples per instance. Iterating that design three times produced the project's headline result, with each intermediate failure diagnosed from retained transcripts (constant fixes teach strings, optional checks collapse into ritual mixtures, and with several fault families even choosing the opening check is oracle-knowledge unless every trajectory opens with one universal read-only triage and branches on the observed anomaly).

Across three mechanically different evidence families, on held-out instances whose repair target appears in zero training trajectories, the trained 3B runs the triage, reads what it finds, and repairs exactly what it observed. Full-solve on the transfer cell goes 0% base, 33% supervised, 58% after a five-round GRPO probe (one family at 8/8), with every single pass mechanically verified against its own episode's evidence and the transfer cell matching or beating in-distribution at every stage. Transfer to an entirely unseen package remains 0%, traced to a build recipe never demonstrated rather than failed diagnosis, which is the next cell to measure.

Generalization is measured, not assumed, and does not move with curriculum size. Tripling the training curriculum from 6 to 18 faults nearly doubled the final GRPO in-distribution rate versus a smaller earlier run on the same environment (28% → 50%), but held-out transfer stayed exactly flat at 1 / 13 (8%) both before and after GRPO on this run. That one pass is a trained fault resampled under the eval harness, not a genuinely unseen instance; every truly held-out cell (unseen fault type, unseen package, unseen composite, unseen combination of both) is 0% for every policy tested, including GRPO. Every fault in the environment, trained or held-out, is proven solvable by its reference fix and unsolved by a naive rebuild before it enters the set. The finding this scaling run was built to test is that training-fault diversity is not the lever that closes the memorization-versus-diagnosis gap. The trained model reliably reproduces more of what it was shown, not how to diagnose something new. An earlier, larger run (13 fault types, ~111 warm-start trajectories, on a since-rebuilt environment, later found to have eval/train overlap in the warm-start data) reached 90% in-distribution; the number above is the more rigorously split, currently reproducible one.

5Frontier difficulty calibration, short-horizon

We measured a frontier model on a representative subset of the short-horizon faults via a sub-agent harness, one attempt each, each result independently confirmed by the harness's own verifier (not the agent's self-report) before the instance was torn down. On the earlier tiers it solved them in 8 to 11 commands. The evidence-lies tranche pushes deeper, 6/6 verified pass in 7 to 18 commands, since whole families of hypotheses must be eliminated when the error blames the wrong thing (the composite fault, two independent root causes in one instance, took the most). An important nuance is that several of those mechanisms are distilled from failures that actually fooled frontier models operating a real system. The benchmark scopes the task ("this package is broken, repair it"), which is easier than the operational original, where the model had to notice the problem itself amid misleading evidence. So the scoped tasks are within frontier reach, which makes this tier's value today its training and evaluation of open models, where it resolves the capability gradient from 0% up.

6The long-horizon tier, built but not yet evaluated

The long-horizon tier restores what the short-horizon tier scopes away, which is exactly the part the operational record shows frontier models failing at. Damage is done early, the symptom appears much later, and the evidence points somewhere else. A fault is seeded into one package of a real LFS build sequence, the build continues normally, and the failure surfaces at a package some distance downstream. The agent gets a shell and a build log, and is never told which package is at fault.

Every instance must pass three machine-checked properties before it counts. The fault must bite (the seeded build fails the verifier), it must be distant (rebuilding only the package where the symptom appears still fails, which is what separates a long-horizon task from a short-horizon fault with extra steps), and it must be solvable (repairing the true cause and rebuilding downstream passes). Three instances currently pass all three, at cause-to-symptom distances of 5, 5, and 14 packages. Two of the five built so far were rejected by that same checker, one measured non-biting and one halted the build at the seed stage. The rejections are worth stating because they show the verification is real. One fault family is verified at both distance 5 and distance 14, so difficulty is a parameter rather than new design work, and 82 packages sit downstream of the seed point as possible symptom sites.

The substrate snapshots the build after every package and can fork an episode from any snapshot, so hundred-step rollouts share one backbone build instead of each paying for its own. This follows three published designs. RLVE motivates difficulty as a tunable generator parameter, applied now. BPO motivates the fork-native substrate, adopted as a design requirement now with the algorithm itself deferred. TRACE shapes the per-turn credit design, which waits on training. The environment already emits the per-turn signals that credit scheme needs, a snapshot diff of the paths each command changed and a non-terminal probe verdict.

Measurement so far is one frontier calibration episode, and nothing more. Claude Fable 5, harness-scored, solved the distance-5 instance in 24 of 40 allowed commands with no information about which package was at fault, by rebuilding the suspect package from its pristine tarball and byte-comparing against the installed artifact to isolate the sabotaged symbol. The scoped short-horizon tasks take the same class of model 7 to 18 commands, so distance already measurably raises difficulty. Beyond that single episode there are no results on this tier. No model has been trained on it, and no multi-sample evaluation has been run. Two further task families mined from live operations incidents in August 2026, one testing whether an agent adapts an install procedure to a live running system rather than a chroot, and one testing diagnosis discipline when the agent's own verifier falsely reports failure, are machine-verified and likewise await evaluation.

7What is included

  • FormatPackaged as a verifiers environment and validated end-to-end against a live model endpoint.
  • DeterminismThe same seed reproduces the same fault and verifier.
  • FootprintRootless sandbox, ~1.6 s/episode, ~200 MB per instance. A full training run cost about $0.50 of GPU.
  • IsolationThe sandbox runs untrusted, agent-generated shell. Its filesystem view is allow-list, only the directories a build needs are kept and everything else on the host is shadowed, with a private loopback-only network. Verified by writing a marker into every host path from inside and confirming none reached the host.
  • IncludedThe short-horizon environment and fault generator, the end-to-end training pipeline and recipe (which reproduces the results above), the calibration harness, and the long-horizon substrate with its verified fault families.
  • ScalingFaults are parameterised over the package, so each new library reuses the whole taxonomy for a small verifier and one entry; the short-horizon set has grown to 74 faults, each proven solvable and biting by CI. On the long-horizon tier, cause-to-symptom distance is a generator parameter.

8Fit and availability

lfs-rl is intended for teams and platforms that train or evaluate open models on agentic, coding, or operations tasks, and for RL-environment marketplaces that require verifiable, hard-to-game rewards.

The environment and its full results remain in a private repository. This page is the standing technical summary of what exists, what has been measured, and what has not.
